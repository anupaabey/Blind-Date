# Security and privacy model

## Trust boundaries

Auth identity comes from a server-verified Supabase user session, not submitted user IDs, route parameters, local storage or editable user metadata. The `proxy.ts` refreshes cookies; every protected page, server action and privileged operation independently verifies identity/role. Role membership is stored in `user_roles`, not user-editable metadata. The service-role client imports `server-only`; no client component imports it.

All public-schema tables use RLS. Authenticated users have read access only to their own sensitive rows. Tables for recommendations, invitations and decisions expose no direct member reads; narrowly shaped `my_invitations` returns only expressly consented anonymous fields, and `my_connections` returns first name/email only after both completed-date feedback submissions grant safe mutual exchange. Admins can read operational records using an explicit role. Internal outbox/rate-limit tables have no member access. Broad client writes and default public function execution are revoked. Workflow functions use a fixed search path and check `auth.uid()`/role inside the database, so bypassing the web UI does not bypass eligibility, mutual decisions or state transitions.

Signup creates a canonical private profile through an Auth trigger with adult DOB, country `LK`, validated Sri Lankan district/town foreign keys, normalized +94 mobile, affirmative residency and consent constraints. Supplying a foreign location, false declaration, invalid phone or underage DOB to the raw Auth endpoint fails. Matching also checks current adult age, eligible status, confirmed email, actual residency review, mutual gender/age/relationship intentions, both location preferences, travel willingness, approximate distance, smoking/drinking dealbreakers, completed questionnaires and blocks/rejections. Demo accounts are confined to other demo accounts.

The scoring implementation in SQL compares actual responses. Category weights are 35/25/20/20; change the versioned scoring function and explanatory UI together if you change them. Missing questionnaires cannot create valid recommendations. Manual recommendations and subsequent approval, acceptance, booking and checkout recheck current eligibility. They do not reveal identities. Declines are final for that pairing. Invitation expiry is checked on each decision.

## Application controls

Server actions use Next.js POST-only actions with framework origin/host CSRF checks, server-side Zod validation and database authorization. Auth provides its own login/signup/verification rate limits. Authenticated mutation buckets use atomic PostgreSQL rate-limit rows. Contact intake uses a server-derived hashed client address and a five-per-hour database bucket; enable an edge WAF/CAPTCHA in production to complement provider limits. Rejections inside a transaction roll back bucket increments, so application limits count successful operations; do not rely on them alone to mitigate adversarial request floods.

Private media objects are non-public, capped at 5 MB, use allowlisted image MIME types and are limited to the owner's folder. No photo is automatically revealed to matches. The MVP does not have a profile-photo gallery UI. Account deletion reauthenticates the current password and removes private media before the Auth user, which cascades personal records. Financial references survive without profile/booking links; minimal de-linked safety/admin audit logs remain. Final retention and statutory obligations require legal review. Third-party provider records must be handled through their own retention procedures.

Headers include CSP, frame denial, no-sniff, restrictive permissions and referrer policy. Browser clients talk only to this origin; Supabase calls occur on the server. CSP allows PayHere form POSTs. Development alone permits `unsafe-eval` for React diagnostics. CSP currently permits inline scripts/styles for Next.js hydration; assess a tested nonce-based policy and deployment-specific HSTS before launch. Protected responses use private/no-store caching. Avoid caching personalized RSC content in an external CDN.

PayHere callback verification uses the provider's prescribed MD5 signature protocol and a timing-safe comparison. It checks merchant, amount, currency, payment mode, order ownership/state and duplicate gateway references before invoking a service-only transition. MD5 is used only because PayHere specifies it, never for password storage. Receipts require the verified callback. Card data never passes through the application. Refunds are tracked requests until an operator actually processes a refund in the merchant portal and records the real reference; automated refund integration is not implemented.

Feedback is private. An unsafe answer opens a private report. Blocking closes the invitation, removes it from both dashboards, cancels active bookings, moves paid bookings to refund review and removes future eligibility/contact exchange. Suspension closes relevant invitations and bookings. Reports and admin actions have an audit trail. Operational review and genuine venue vetting are human responsibilities, not automatic guarantees.

## Launch limitations

A local passing suite is evidence of the implemented development workflow, not a penetration test, legal opinion, proof of residency, deliverability test, payment-provider certification or guarantee of safety. Admin MFA enforcement, financial reconciliation/chargeback handling, retention automation, scheduled backups/restore drills, provider webhook tests and operational incident coverage must be reviewed before live launch. No sensitive identity document collection, IP residence gating, public profiles, international matching or global venue booking is implemented.
